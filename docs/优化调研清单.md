## 一、性能

### 1.1 高频 JSON 写盘的批量合并（去抖/节流）
- **现状**：`FragmentManager.add_fragment`、`delete_fragment` 等每个增删都立即 `_save()`（原子写）；剪贴板监听每次变化都会触发写盘。长时间复制会频繁触发 `fragments.json` 全量序列化＋磁盘写。
- **建议**：引入「写盘去抖」——内存变更后延迟 ~500ms~1s 合并一次落盘，或在 N 次变更后批量落盘；崩溃最多丢失窗口期内的少量数据（可接受）。
- **适用场景**：用户大量复制/批量操作时，减少 I/O 抖动与 SSD 写入放大。
- **预期收益**：高频场景磁盘写次数下降一个数量级，UI 卡顿减少；风险极低。

### 1.2 紧凑 JSON（去除 `indent=2`）
- **现状**：所有 `_save()` 都 `json.dump(..., indent=2)`，文件体积与序列化时间偏大。
- **建议**：数据文件改用紧凑格式（`indent=None`，必要时 `separators=(',', ':')`）；仅用户可读的 `config.json` 可保留缩进。或引入 `orjson`/`ujson` 加速序列化。
- **适用场景**：`fragments.json`/`notes.json`/`schedule.json` 数据量大时。
- **预期收益**：文件体积约降 30%，序列化更快；风险极低。

### 1.3 大列表渲染的虚拟化 / 增量更新
- **现状**：`MainWindow`（3313 行）的碎片/任务/笔记列表在刷新时往往整体重建；`AppLauncherPage._render_cards` 每次尺寸变化或数据变化都 `deleteLater` 全部卡片再重建。
- **建议**：改用 `QListWidget`/`QTableView` + 模型（`QAbstractListModel`）配合 `beginResetModel/endResetModel`，或仅更新变化行；卡片网格在列数不变时避免整体重建。
- **适用场景**：碎片/素材数量达到数百上千条时滚动与刷新变卡。
- **预期收益**：大列表渲染耗时与内存显著下降；中等改动量。

### 1.4 图标加载缓存（`QPixmapCache`）
- **现状**：`widget_app_launcher.py` 中 `extract_exe_icon`/`load_icon_pixmap` 每次渲染卡片都重新从 exe 提取或读文件，`QFileIconProvider` 调用较贵。
- **建议**：用 `QPixmapCache`（按 "path@size" 作 key）缓存提取结果，仅在 exe 路径失效时失效。
- **适用场景**：软件导航卡片较多且频繁刷新/切换时。
- **预期收益**：卡片渲染更快、磁盘/系统调用减少；低风险。

### 1.5 docx 指纹检测避免整文件 sha1（大文档）
- **现状**：`DocxManager._file_fingerprint` 每次启动与保存都读全文件算 sha1（8KB 分块）。知识库很大时成本上升。
- **建议**：优先只比 `mtime`；仅当 `mtime` 变化再算 sha1 确认内容变更（当前已存 `last_mtime`，但 `_file_fingerprint` 仍每次算 sha1）。可改为「mtime 一致即视为未改」。
- **适用场景**：知识库.docx 体积大、启动频繁时。
- **预期收益**：启动检测更快；低风险（需确认 mtime 精度足够）。

### 1.6 剪贴板监听去重的 `os.path.exists` 调用
- **现状**：`ClipboardMonitor._parse_and_add` 对多行文本逐行 `os.path.exists` 判断是否为路径；文件很多时系统调用较多。
- **建议**：路径判定仅对明显像路径的行（含盘符/分隔符、长度阈值）做 `exists` 检查，减少无效系统调用。
- **适用场景**：用户常复制大段多行文本时。
- **预期收益**：小幅 CPU 下降；低风险。

## 二、结构 / 可维护性

### 2.1 拆分巨型 `main_window.py`（3313 行）
- **现状**：`MainWindow`（102 行起）＋ `MergePreviewDialog` 全部挤在一个 3313 行文件里，含 5 个面板、127 个方法/函数；`card_window.py` 1516 行、`widget_app_launcher.py` 1040 行、`theme.py` 886 行也偏大。
- **建议**：按面板拆分为独立文件（如 `panels/fragment_panel.py`、`task_panel.py`、`note_panel.py`、`knowledge_panel.py`、`settings_panel.py`），`MainWindow` 仅做容器与信号桥接。
- **适用场景**：后续要持续加功能/多人协作时，单体文件会让合并冲突与定位成本飙升。
- **预期收益**：可维护性大幅提升、review 更容易、回归风险降低；改动较大，建议配合测试一起做。

### 2.2 减少 `main()` 中过长的「信号槽桥梁」
- **现状**：`knowledge_ball.py` 的 `main()` 末尾有 8+ 处信号槽连接，且大量通过 `ball._card_window._xxx` 这种**私有属性穿透**访问（如 `ball._card_window._last_mode`）。
- **建议**：把跨组件协作接口提升为公开方法/信号（如 `CardWindow.reset_to_home()`、`MainWindow.safe_quit()`），避免直接戳私有成员；桥梁逻辑可抽到独立 `wiring.py`。
- **适用场景**：只要还在改动交互逻辑就值得；否则暂时稳定。
- **预期收益**：降低耦合、减少「改一处崩三处」；中等改动。

### 2.3 引入类型注解 + 静态检查（mypy/pyright）
- **现状**：项目已有 `pyrightconfig.json`，但源码函数大多无类型注解。
- **建议**：逐步为公共方法补 `type hints`，并接入 `pyright`/CI；先覆盖 manager 层（数据核心），UI 层可暂缓。
- **适用场景**：作为长期质量基线，配合 2.1 拆分一起推进效果最好。
- **预期收益**：提前发现空值/类型错误，重构更安全；渐进式。

### 2.4 统一常量与魔法数字
- **现状**：大量散落的魔法数字/字符串（主题色 `#5BC0BE` 在 `theme.py` 与 `widget_app_launcher.py` 各写一份；`temp_asset_max_count` 默认值在 `config.py` 与 `temp_asset_manager` 文档注释里不一致）。
- **建议**：主题色全部走 `theme.py` 颜色字典（已是方向，需清理 `widget_app_launcher` 里硬编码的 `#5BC0BE`）；默认值集中到一处。
- **适用场景**：避免「改色改一半」类问题；低成本。
- **预期收益**：一致性、减少隐藏 bug。

### 2.5 README 与实际代码/文件名不一致
- **现状**：README 写入口是 `knowledge_ball.py`、spec 叫 `知识卡片悬浮球.spec`，实际入口确为 `knowledge_ball.py`，但根目录有 `FloatPulse.spec` 和 `build.spec` 两个 spec；README 的文件结构章节未提及 `nav_manager`、`temp_asset_manager`、`widget_app_launcher` 等新增模块。
- **建议**：统一打包入口（保留一个 spec），同步 README 的文件结构/章节。
- **适用场景**：要对外发布/交接时必做。
- **预期收益**：降低新人上手与发布出错成本；低成本。

## 三、安全性

> 本项目是**本地常驻 Windows 桌面工具**，攻击面主要来自「用户配置/外部文件/网络下载」，而非网络暴露。以下按风险真实度排序。

### 3.1 `subprocess.Popen` 启动外部 exe —— 当前已安全，建议保留并加固
- **现状**：`widget_app_launcher.launch_app` 用 `subprocess.Popen([exe_path, ...], shell=False)`，参数以列表传入，**未启用 shell**，路径来自用户自己配置的 `apps` 列表。这是安全写法，无命令注入风险。
- **建议**：保持 `shell=False`；对 `launch_args` 的 shlex 解析可增加白名单校验（仅当未来允许用户输入任意参数时必要）。当前风险：**低**。
- **适用场景**：维持现状即可，是正面范例。

### 3.2 浏览器拖拽图片时的 **HTTP 下载**（`_download_url`）
- **现状**：`knowledge_ball.py` 的 `dropEvent` 在本地文件/FileContents/图片 MIME 都没有命中时，会**主动用 `QNetworkAccessManager` 下载任意 HTTP/HTTPS URL** 并保存到 `temp_assets/`。URL 来自拖拽数据，理论上可被恶意网页构造。
- **建议**：
  - 限制协议为 `http/https` 且**禁止指向本地/内网**（防止 SSRF 类把 `file://`、内网地址当图片拖入）；
  - 限定下载大小上限（避免大文件写满磁盘）；
  - 下载后按真实文件头（magic bytes）校验类型，而非仅靠 URL 后缀猜扩展名；
  - 考虑默认**关闭**自动下载，改为弹窗询问（用户拖网页图片本意常为「存这张图」，但自动下载有被滥用的可能）。
- **适用场景**：只要保留「拖网页图片自动落盘」功能就值得加固。
- **预期收益**：堵住潜在的任意下载/磁盘写放大/伪装文件风险；中等改动。

### 3.3 文件名校净化已做，但需覆盖更多落盘点
- **现状**：`_save_file_contents` 已清洗 `\/*?:"<>|`；但 `_download_url` 用 URL 路径猜扩展名，且 `_save_mime_image` 用固定 `.png`，整体较稳。
- **建议**：所有「外部输入 → 落盘文件名」路径统一走一个 sanitize 函数（含长度限制、非空、去父目录 `..`）。
- **适用场景**：作为 3.2 的配套加固。
- **预期收益**：防止路径穿越/伪装文件；低成本。

### 3.4 全局异常钩子打印完整 traceback 到弹窗
- **现状**：`_install_global_excepthook` 把完整异常栈显示给用户（也可能含路径/文件名）。本地单用户工具风险有限，但信息泄露不必要。
- **建议**：弹窗只显示**友好的错误摘要**＋「日志已记录到 data/app.log」；完整栈仅写日志。
- **适用场景**：任何对外分发版本都应做。
- **预期收益**：减少敏感路径/用户名暴露；极低风险。

### 3.5 依赖与构建环境安全
- **现状**：`requirements.txt` 固定了 `PyQt6==6.7.1`、`python-docx==1.1.2`、`pyinstaller==6.10.0`；但打包在 dev 机全局环境进行。
- **建议**：用**干净虚拟环境**（venv）打包，避免把 dev 机多余库打进去（也顺带减小体积）；可引入 `pip-audit` 周期性扫描依赖漏洞。
- **适用场景**：准备正式发布时。
- **预期收益**：减小包体、降低供应链风险；低成本。

## 四、打包 / 分发

### 4.1 `--onefile` vs `--onedir` 选择
- **现状**：`FloatPulse.spec` 用的是 `COLLECT` + `EXE(exclude_binaries=True)`，即 **onedir（目录）模式**；但 README 里又示例了 `--onefile`。两处口径不一致。
- **社区结论**（检索一致）：
  - `--onefile`：分发单个 exe 方便，但**每次启动都要解压临时文件**，冷启动 5–10s；且更易触发杀软误报（压缩二进制＋运行时解包特征）。
  - `--onedir`：启动快（1–2s）、误报率低，但需分发整个文件夹（可用 Inno Setup/NSIS 做安装包包裹）。
- **建议**：正式发布用 **onedir ＋ 安装包封装**（与现有 spec 一致，需清理 README 的 onefile 误导）；若坚持单文件，接受启动慢并考虑代码签名降低误报。
- **适用场景**：发布形态决策，需你拍板。
- **预期收益**：更快启动、更低误报、更专业的安装体验。

### 4.2 关闭 UPX 或谨慎排除
- **现状**：spec 里 `upx=True`。UPX 虽减小体积 ~25%，但**被大量恶意软件使用，会显著抬高杀软误报率**。
- **建议**：对外分发版本考虑 `--noupx`；若要用，至少 `--upx-exclude` 排除 `vcruntime*.dll`、`Qt*.dll` 等（压缩后加载异常/更慢）。
- **适用场景**：重视「用户下载后不被杀软拦」时。
- **预期收益**：误报率下降；代价是包体略大。

### 4.3 代码签名（EV 证书）
- **现状**：spec 中 `codesign_identity=None`，未签名。
- **建议**：公开分发务必用代码签名证书（DigiCert/Sectigo 等，约 $200/年）签名 exe；否则 Windows SmartScreen 会拦截「Windows 已保护你的电脑」。
- **适用场景**：面向陌生用户分发时必备。
- **预期收益**：消除 SmartScreen 拦截，提升可信度；需付费。

### 4.4 精简打包体积
- **建议**：干净 venv 打包；`excludes` 排除未用模块（如 `tkinter`、`unittest`、`email` 等标准库大件若未用）；`strip=True` 去符号表。
- **适用场景**：减小下载体积。
- **预期收益**：包体可降 30%+；低风险。

## 五、测试 / 质量保障

### 5.1 当前测试覆盖薄弱
- **现状**：仅有 `test_init.py`（启动冒烟）与 README 提到的 `_syntax_check.py`；manager 层核心逻辑（去重、trim、json 损坏回退、docx 增量同步）**无单元测试**。
- **建议**：为纯逻辑层（FragmentManager / TaskManager / NoteManager / ConfigManager / DocxManager）补 `pytest` 单元测试，不依赖 GUI；UI 层用 `pytest-qt` 做关键交互冒烟。
- **适用场景**：任何后续重构（尤其 2.1 拆分）前必须先建测试护栏。
- **预期收益**：重构安全网、回归成本下降；一次投入，长期受益。

### 5.2 引入 `pytest-qt` 做 UI 冒烟
- **现状**：无。
- **建议**：用 `pytest-qt` 的 `qtbot` 模拟点击/输入，验证面板切换、主题切换、碎片增删不崩；CI 中跑（Windows runner）。
- **适用场景**：作为发布前的自动冒烟。
- **预期收益**：减少「手动点一遍才发现崩了」；中等投入。

### 5.3 安全静态扫描（Bandit）
- **现状**：无。
- **建议**：CI 里跑 `bandit -r src` 检测 `shell=True`、危险 `eval` 等；本项目目前无明显问题，但建立基线有益。
- **适用场景**：长期质量门禁。
- **预期收益**：防止未来引入安全反模式；低成本。
