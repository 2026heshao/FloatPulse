## 1. 边界：什么该做插件，什么不该

| 类别 | 归属 | 例子 |
|---|---|---|
| 球本体、卡片 6 模式、拖放分流 | **核心内置，不可插件化** | 悬停弹卡 / 滚轮翻卡 / 拖文件进球 |
| 六大内置功能 | **核心内置，不可插件化** | 碎片 / 任务 / 笔记 / 网址 / 素材 / 软件 |
| 新增的「专精单一功能」 | **走插件** | 屏幕取色、剪贴板历史、去格式粘贴 |

为什么要划这条线：悬浮球的交互通道只有 7 条且已全部占满（悬停 / 单击 / 双击 /
滚轮 / 右键 / 拖放 / 热键）。再往球里堆功能只能靠「右键菜单加层级、抢新热键、
改现有手势」，三条都会毁掉「快」。插件机制让新功能独立进出，不欠技术债。

## 2. 插件包结构

```
plugins/color-picker/
  manifest.json    必需 —— 声明，宿主的唯一真相源
  plugin.py        必需 —— 入口模块
  icon.png         可选 —— 右键菜单图标（24×24 左右，png）
  使用说明.md      强烈建议 —— 插件中心页面会显示其中的一句话摘要
                   （卡片取正文第一段，约 90 字；「查看使用说明」按钮打开全文）
```

> 使用说明文件名约定：优先识别 `使用说明.md`，兼容 `README.md`。
> 摘要提取规则：跳过标题行和表格行，取第一条正文文字。

分发格式 `<id>.fpplug`（**本质就是 zip**）。宿主启动时会扫描
`plugins/*.fpplug`，**自动解压到 `plugins/<manifest.id>/` 再加载，解压后保留原
`.fpplug` 文件**。运行时只加载文件夹，不使用 zipimport。

> 插件目录位置 = `<base_dir>/plugins/`。源码运行即项目根 `FloatPulse/plugins/`；
> 打包运行即 exe 同级 `plugins/`。目录不存在时程序会自动创建，不报错。
>
> ⚠️ **别和 `float_data/plugins/` 搞混**——那是两个完全不同的目录：
>
> | 目录 | 用途 | 谁写 |
> |---|---|---|
> | `<base_dir>/plugins/` | **插件安装位置**：一个插件一个子目录，放这里才会被加载 | 你（开发者/用户）手工放 |
> | `float_data/plugins/<plugin_id>/` | **插件私有数据**：插件自己落盘的状态（`ctx.data_dir`） | 插件运行时自己写 |
>
> 简记：**装插件放 `plugins/`，插件的数据落在 `float_data/plugins/`**。
> 插件中心页面顶部会直接显示当前安装目录的**绝对路径**，拿不准就照抄那行。

## 3. manifest.json 字段表

| 字段 | 类型 | 必需 | 说明 |
|---|---|---|---|
| `id` | str | ✅ | 插件唯一标识，同时用作目录名。字母数字开头，可含 `. _ -`，1–64 位 |
| `name` | str | ✅ | 展示名 |
| `version` | str | ✅ | 版本号（自由格式字符串） |
| `entry` | str | ✅ | 入口模块文件名，如 `plugin.py`。不允许绝对路径或 `..` |
| `requires` | list[str] | ❌ | 依赖声明（**白名单校验**，见下） |
| `actions` | list[obj] | ❌ | 动作声明（**声明唯一真相源**） |
| `actions[].id` | str | ✅ | 动作 id，**全局唯一**，建议 `<插件id>.<动作名>` |
| `actions[].title` | str | ✅ | 菜单/日志展示用标题（插件代码未设 title 时作兜底） |
| `actions[].hotkey` | str | ❌ | 全局热键，如 `"Ctrl+Alt+C"`；必须含修饰键 |
| `actions[].menu` | bool | ❌ | `true` → 挂到悬浮球右键菜单，默认 `false` |
| `capabilities` | list[str] | ❌ | 能力声明（2026-09-27 起）。合法值：`"network"`（网络桥，见 4.1）、`"write"`（只增写入口，见 4.3）、`"manage"`（改删入口，**蕴含 write**，见 4.5）；未知能力名 → **拒载**（防拼写错误静默失效） |
| `page` | obj | ❌ | 页面插件声明（2026-09-27 起）。`{"title": "🤖 AI 助手"}`——在主窗口侧栏加一个导航页（见 4.2 节）；title 必须是非空字符串，否则拒载 |
| `api_version` | int | ❌ | 插件契约版本（2026-09-27 起），缺省 `1`。非正整数 → 拒载；**高于宿主**（当前为 1）→ 拒载，失败阶段 `version_mismatch` |
| `min_app_version` | str | ❌ | 要求的最低程序版本（2026-09-27 起），如 `"4.6.0"`，缺省 `""` = 不限制。必须点分数字，否则拒载；宿主版本低于它 → 拒载 |

示例：

```json
{
  "id": "color-picker",
  "name": "屏幕取色",
  "version": "1.0.0",
  "entry": "plugin.py",
  "requires": ["PyQt6.QtGui"],
  "actions": [
    {"id": "color-picker.pick", "title": "屏幕取色", "hotkey": "Ctrl+Alt+C", "menu": true}
  ]
}
```

## 4. 依赖白名单（硬性）

**只允许 PyQt6 + Python 标准库。** 校验规则（`is_allowed_requirement`）：

- 只校验顶层模块名（`urllib.request` → `urllib`）
- `PyQt6` 及其子模块 ✅
- 标准库模块名 ✅（按 `sys.stdlib_module_names` 判定）
- **显式拒绝**：`ssl` / `_ssl` / `socket` / `http` / `urllib` / `ftplib` /
  `smtplib` / `telnetlib` / `requests` / `urllib3` / `httpx` / `aiohttp` /
  `websockets`
- 名字里出现 `/` `\` `:` 或为 `.` / `..` → 拒绝

> 为什么连标准库的 `ssl` 都拒：**插件永远不直接持有网络库**。
> 需要联网的插件走「能力声明 + 宿主网络桥」（见 4.1），而不是自己 import。

`requires` 里出现白名单外的名字 → **整个插件被拒绝加载**，日志写明原因。

### 4.1 联网：capabilities + 宿主网络桥（2026-09-27 起）

插件联网的正确姿势——**声明能力、使用宿主桥**，插件代码里一行网络库都不出现：

```json
{ "capabilities": ["network"] }
```

```python
ok = ctx.http_post_json_async(
    "https://api.deepseek.com/v1/chat/completions",
    headers={"Authorization": "Bearer <key>"},
    body={"model": "deepseek-chat", "messages": messages},
    timeout=60.0,
    on_done=self._on_reply,      # result dict，见下；保证在 UI 线程回调
)
```

规则与行为：

- 未声明 `network` 的插件调用桥 → 安全拒绝：返回 `False` 且 `on_done`
  收到一次 `{"ok": False, "error": ...}`，**不抛异常**
- 宿主在后台线程发请求；`on_done(result)` 保证回 UI 线程，可直接更新控件
- `result` 字段：`ok` / `status` / `body`（响应文本）/ `error` / `url`
- 限制：timeout ≤ 120s；响应上限 4MB；每次请求只记 **URL + 耗时** 进
  `app.log`（`[插件网络]` 行），请求体与响应体不落日志
- 审计与信任：插件中心卡片会显示「🌐 网络访问」标记，用户可见插件会联网；
  插件**不得**静默上传宿主数据（参考 `plugins/ai-assistant/` 的做法：
  只在用户显式点快捷指令或发送消息时才发请求）
- `ctx.has_capability("network")` 可在运行时自检能力

完整示例见 `plugins/ai-assistant/`（本地 Ollama / llama-server 与云端
DeepSeek 双后端）。

### 4.2 页面插件：manifest `"page"` + `create_page()`（2026-09-27 起）

适合功能完整的重量级插件（如 AI 助手）：不再挤悬浮球菜单，而是直接在
主窗口侧栏拥有一个导航页。

```json
{ "page": { "title": "🤖 AI 助手" } }
```

```python
class MyPlugin(BallPlugin):
    def create_page(self, ctx: PluginContext):
        return MyPage(ctx)       # QWidget 子类；返回 None = 没有页面
```

行为与约束（宿主 `register_plugin_page()` 统一处理，插件无需关心）：

- 页面物理索引 = QStackedWidget 末尾（固定页 0–9 之外，插件页 10+）；
  侧栏按钮插在「设置」按钮之前
- 插件页**不参与**侧栏拖动换位、**不写入** `last_page_index`
  （config 对该键有上限校验，越界写入会被静默丢弃）
- **注册幂等**：插件中心「重新扫描」会重跑装配并重建页面，同一插件
  重复注册只替换页面内容，索引与侧栏按钮保持稳定
- 页面样式自动跟随主窗口 QSS 与 light/dark 主题（页面挂在主窗口
  contentArea 之下，`glassCard` / `primaryBtn` / `secondaryBtn` /
  `fieldLabel` / `sectionLabel` / `hintLabel` 直接可用）
- 打开页面的约定入口：`ctx.parent_window().show_plugin_page("plugin:<插件id>")`
  （未知 key 或固定页 key 返回 `False`）；热键路径开页面记得先
  `QTimer.singleShot(0, ...)` 延后，见第 12 节
- 页面若订阅了全局单例（如 `LOCAL_SERVER`），在 `destroyed` 信号里退订，
  防止重建后的死引用累积（`ai-assistant/plugin.py` 有示例）

### 4.3 受限写能力：`capabilities: ["write"]` + `ctx.write`（2026-09-27 起）

默认情况下插件**只能读**（`ctx.data` 是只读快照）。需要把结果写回应用
（例如「把 AI 整理结果存成笔记」）的插件，声明 `write` 能力后可用
`ctx.write` 新增数据：

```json
{ "capabilities": ["write"] }
```

```python
nid = ctx.write.add_note("本周小结", 全文)      # 返回 note_id，0 = 未写入
fid = ctx.write.add_fragment("随手记的内容")     # source 自动补 "插件:<插件id>"
tid = ctx.write.add_task("交周报", note="附数据", deadline="2026-10-01")
kb  = ctx.write.add_knowledge("要追加到知识库的一段话")   # 返回编号（从 1 起），0 = 未写入
```

规则与边界：

| 项 | 说明 |
|---|---|
| 权限 | 未声明 `write` 就调用 → 记 warning 并返回 `0`，**不写数据、不抛异常** |
| 只增不改删 | 门面上**只有** `add_fragment` / `add_task` / `add_note` / `add_knowledge`，没有 update / delete |
| 返回值 | 新记录的 id（`fragment_id` / `task_id` / `note_id`）；`add_knowledge` 返回**段落编号**（不是 id）；`0` = 失败 |
| 内容护栏 | 空串 / 纯空白 / 非字符串 → 拒写；超 8000 字符 → 截断后照写（不拒写）；知识库段落**少于 4 个字**会被拒（过滤规则，见 11 节） |
| 来源可追溯 | 碎片的 `source` 缺省为 `插件:<插件id>`，可在碎片页看到来源 |
| UI 联动 | 写入成功后宿主自动刷新对应面板与悬浮球徽标，与手动新增一致 |
| 用户可见 | 插件中心卡片显示「✍ 写入数据」标记，用户能看到插件会改数据 |

自检：`ctx.write.enabled()` / `ctx.has_capability("write")`；
`ctx.write.sources()` 返回宿主实际注入的通道（`fragment` / `task` / `note` /
`knowledge`）。

> **知识库写入前会先查外部改动**：`.docx` 的保存是**整篇回写**，如果你在 Word
> 里改过而宿主内存模型还是旧的，落盘会把你的改动整篇覆盖。所以宿主在写之前
> 先 `check_external_modification()`，命中就拒绝并在日志记 warning——调用方
> 拿到的还是 `0` / `False`，不需要额外判分支。用户侧的解法是到知识库页点
> 「🔄 重新加载」。

> **不要**试图绕过它去 import 管理器或直接写 json——这既会被依赖白名单拦下，
> 也违反插件契约（见第 1 节）。

参考实现：`plugins/ai-assistant/` 的 AI 回复气泡底部有「📥 存为笔记」按钮。

### 4.4 版本契约：`api_version` / `min_app_version`（2026-09-27 起）

宿主与插件之间有版本握手，避免 API 演进后老插件以「动作创建失败」这类
表层错误暴露：

```json
{
  "api_version": 1,
  "min_app_version": "4.6.0"
}
```

| 字段 | 缺省 | 规则 |
|---|---|---|
| `api_version` | `1` | 非正整数 → 拒载；**大于宿主** `PLUGIN_API_VERSION`（当前 1）→ 拒载 |
| `min_app_version` | `""` | 必须点分数字（`"4.6.0"`），否则拒载；宿主版本低于它 → 拒载 |

拒载时失败阶段是 **`version_mismatch`**（面板显示「版本不匹配」），
修复建议是「升级 FloatPulse 或联系插件作者」——与「manifest 写错了」区分开，
用户不会被误导去改配置。

> 写插件的两条建议：
> - `api_version` **不要**主动填，除非你确实用到了某个新契约；
> - `min_app_version` 填你**实际兼容的最低版本**，别填当前最新版，
>   否则会把还留在旧版的用户全部挡掉。

版本常量在 `src/app_version.py`：`APP_VERSION`（程序版本）、
`PLUGIN_API_VERSION`（契约版本，破坏性变更才 +1）。

### 4.5 改删能力：`capabilities: ["manage"]` + `ctx.manage`（2026-09-28 起）

`write` 只能新增。需要**修改或删除**既有数据的插件（例如「把这条任务标记
完成」「删掉那条重复碎片」）要单独声明更高一档的 `manage`：

```json
{ "capabilities": ["manage"] }
```

```python
ctx.manage.set_task_done(3, True)                 # 标记完成 → bool
ctx.manage.update_task(3, title="新标题")          # None = 该字段不动 → bool
ctx.manage.update_note(5, content="改后的正文")
ctx.manage.update_fragment(2, content="改后的内容")

token = ctx.manage.delete_task(7)                 # 删除 → 撤销令牌（0 = 失败）
ctx.manage.undo_delete(token)                     # 误删后恢复 → bool

# 知识库：位置型标识，必须带内容指纹（见下面「位置型数据」）
snap = ctx.data.knowledge()                       # 先读快照拿到 num + hash
cur  = next((p for p in snap if p["num"] == 4), None)
ctx.manage.update_knowledge(cur["num"], "改写后的段落", cur["hash"])   # → bool
token = ctx.manage.delete_knowledge(cur["num"], cur["hash"])          # → 撤销令牌
```

**`manage` 蕴含 `write`**：声明了 `manage` 的插件同时拿到 `ctx.write` 的
三个 `add_*`——改删必然要先能读能写，拆成两个独立开关只会让插件作者困惑。

| 项 | 说明 |
|---|---|
| 权限 | 未声明 `manage` 就调用改删方法 → 记 warning 并返回 `False` / `0`，**不动数据、不抛异常** |
| 只声明 `write` ≠ 拿到 `manage` | 两档分开判定；写权限不会顺带升级成改删权限 |
| 部分更新语义 | `update_*` 的文本参数 `None` = **该字段不动**（给值才改）。这样弱模型不必为「只改标题」重复回填正文 |
| 删除可撤销 | `delete_*` 返回**撤销令牌**（正整数，`>0` 成功）；调用方留着令牌，用户后悔时调 `undo_delete(token)` |
| 令牌一次性 | 一个令牌只能用一次；重复撤销返回 `False` |
| 撤销的代价 | 任务/碎片/笔记走「重新插入」路径（`add_*` 是唯一入口），**恢复后记录 id 可能是新的**，标题/正文/完成态/专注次数原样还原 |
| 撤销栈容量 | 宿主只保留最近 **50** 次删除的快照，更早的令牌失效 |
| 参数护栏 | id / 令牌必须是**真整数**（`bool` 是 `int` 子类，会被拒）；文本参数给了就必须是 `str` |
| 审计 | 每次改删都记 `[插件管理] <插件id> <方法><参数> -> <结果>` 进日志 |
| UI 联动 | 成功后宿主自动刷新对应面板与悬浮球徽标 |
| 用户可见 | 插件中心卡片显示「🛠 改删数据」标记 |

#### 位置型数据：知识库改删必须带 `expect_hash`

任务 / 碎片 / 笔记用**自增 id**，删了不会复用，拿到旧 id 顶多失败。知识库不同：

| 特征 | 后果 |
|---|---|
| 用**编号（位置）**寻址 | 删掉第 3 段，原第 5 段变成第 4 段 → 缓存下来的 `num` **随时是过期引用** |
| `.docx` 可被 Word / WPS **外部编辑** | 用户改一段、删一段，宿主内存模型没变 → 编号指向的段落已经换了 |

所以这两个方法**多一个必填参数**，且**没有「不校验」的选项**：

```python
ctx.manage.update_knowledge(num, content, expect_hash)   # → bool
ctx.manage.delete_knowledge(num, expect_hash)            # → 撤销令牌
```

| 项 | 说明 |
|---|---|
| `expect_hash` | 你**读快照时**那一段的 `hash`。宿主写之前重新算一遍当前内容，**对不上直接拒绝**（返回 `False` / `0`），不做任何修改 |
| 传空 / `None` / 非字符串 | 一律拒（`_check_hash` 比文本参数严：**没有「不校验」这个选项**） |
| `num` 越界 | 拒。`num` 必须是 `>= 1` 的真整数 |
| `content` 护栏 | 空串 / 纯空白 / 非字符串 → 拒；少于 4 个字 → 拒（会被过滤规则吃掉） |
| 外部改动闸门 | 命中 `check_external_modification()` → 拒绝并记 warning（`save()` 是整篇回写，会覆盖用户在 Word 里的改动） |
| 撤销语义不同 | 任务/碎片/笔记撤销是「重新插入」（id 变新）；知识库撤销用 `insert_paragraph_before` **放回原位置**——对位置型数据，位置本身就是信息 |

> **给「让 AI 改知识库」的插件的建议**：把 `hash` 当成「这一段现在是这个内容」
> 的凭据，从快照里原样透传，**不要自己去算、也不要凭空生成**。同一条指令里
> 有多个知识库删除时，**必须按编号降序执行**——否则删完第一个，第二个的编号
> 已经前移了。参考实现见 `plugins/ai-assistant/plugin.py` 的 `_order_actions()`。

自检：`ctx.manage.can_manage()` / `ctx.manage.manage_sources()`（宿主实际
注入的通道名）。`ctx.write` 与 `ctx.manage` 是**同一个门面对象**，只是按
语义分名字用——门禁在方法级按能力名判定，用 `ctx.manage` 调 `add_note`
也一样要过 `write` 那一关。

> **给「让 AI 改数据」的插件的建议**：能力声明只是最后一道闸，它不能替
> 你判断「这条指令该不该执行」。参考实现 `plugins/ai-assistant/` 的做法是
> **分级确认**——新增类直接执行（错了容易删），改删类先渲染一张确认卡、
> 用户点「执行」才落库，删除成功后给「↩ 撤销删除」；解析失败时**整块不
> 执行并如实提示**，绝不猜用户意图。详见第 14 节。

## 5. 最小可用插件

`plugins/hello/manifest.json`：

```json
{
  "id": "hello",
  "name": "示例插件",
  "version": "1.0.0",
  "entry": "plugin.py",
  "requires": [],
  "actions": [
    {"id": "hello.say", "title": "打个招呼", "hotkey": "Ctrl+Alt+H", "menu": true}
  ]
}
```

`plugins/hello/plugin.py`：

```python
# -*- coding: utf-8 -*-
from src.plugin_api import BallAction, BallPlugin


class SayHello(BallAction):
    id = "hello.say"
    title = "打个招呼"          # 可省略，省略时用 manifest 的 title

    def run(self, ctx):
        # ctx 是宿主给的白名单能力，只有下面这些：
        #   ctx.logger           -> 日志器（写进 data/app.log）
        #   ctx.config           -> 只读配置快照（MappingProxyType，改不了）
        #   ctx.show_toast(t, ms)      -> 弹主窗口轻提示
        #   ctx.open_main_window()     -> 打开主窗口
        #   ctx.open_card_mode(mode)   -> 弹小卡片并切模式
        #                                fragment/task/note/nav/asset/app
        #   --- 数据与身份（详见第 11 节）---
        #   ctx.data             -> 只读数据门面（任务/碎片/笔记/番茄）
        #   ctx.write            -> 受限写入口（需声明 write 能力，见 4.3）
        #   ctx.manage           -> 改删入口（需声明 manage 能力，见 4.5）
        #                          含撤销：delete_* 返回令牌 → undo_delete
        #   ctx.plugin_id        -> 插件 id 字符串
        #   ctx.plugin_dir       -> 插件包所在目录
        #   ctx.data_dir         -> 插件私有数据目录（首次访问自动创建）
        #   ctx.parent_window()  -> 主窗口引用（挂对话框用）
        #   --- 可选能力（需在 manifest 声明，见 4.1 / 4.3 / 4.5）---
        #   ctx.http_post_json_async(...) -> 联网（network）
        #   ctx.has_capability(name) / ctx.capabilities()
        #   ctx.write.can_manage() / ctx.manage.manage_sources()
        ctx.logger.info("hello 插件被触发")
        ctx.show_toast("你好，我是外置插件 ✋")


class HelloPlugin(BallPlugin):
    id = "hello"
    name = "示例插件"
    version = "1.0.0"

    def create_actions(self, ctx):
        return [SayHello()]
```

`id` / `name` / `version` 会被 manifest 覆盖（manifest 是真相源），
所以两边保持一致最好，写错也不会出错。

## 6. 安装 / 打包 / 卸载

| 动作 | 操作 |
|---|---|
| 安装（文件夹） | 把插件文件夹放进 `plugins/`，点插件中心「🔄 重新扫描」即可，无需重启 |
| 安装（压缩包） | 把 `<id>.fpplug` 放进 `plugins/`，点「🔄 重新扫描」（自动解压） |
| 打包 | **用打包器**：`python tools/pack_plugin.py plugins/<你的插件> [--force]`（2026-09-28 起）。手工打包也可：压成 zip 重命名为 `<id>.fpplug`，zip 内 `manifest.json` 在根目录或整体套一层同名目录都可 |
| 临时禁用（单个） | 插件中心卡片上的「⏸ 停用」——**状态会记住，重启后仍为停用**（2026-09-27 起） |
| 临时禁用（全部） | 设置页「悬浮球插件」总开关关掉（立即生效，模块仍驻留内存） |
| 卸载 | 插件中心卡片上的「🗑 卸载」→ 二次确认（列出将被删除的绝对路径）→ 删除插件目录 |

> **卸载的边界**（2026-09-27 起）：卸载会 `rmtree` 插件目录、摘掉动作 /
> 热键 / 菜单项 / 插件页面，并清掉模块缓存（`sys.modules`），
> 因此之后「重新扫描」不会把它复活。

### 打包器 `tools/pack_plugin.py`（2026-09-28）

```
python tools/pack_plugin.py plugins/ai-assistant              # 打到项目根 plugin_store/
python tools/pack_plugin.py plugins/ai-assistant --force      # 覆盖同名旧包
python tools/pack_plugin.py plugins/ai-assistant --check-only # 只校验（提交前 / CI 自检）
python tools/pack_plugin.py plugins/ai-assistant -o 其他目录    # 换输出目录
```

它在**打包期**就把装载期才会暴露的问题挡下来，不必等用户装进程序看到「加载失败」：

| 校验项 | 触发时给出的提示 |
|---|---|
| `manifest.json` 可读 / UTF-8 / 合法 JSON | 中文乱码会提示「别存成 GBK」 |
| manifest 结构（复用 `validate_manifest`，规则不重写） | 缺字段 / id 非法 / entry 越界等 |
| `requires` 依赖白名单 | 列出违规项 + 替代路径（联网改用 `capabilities:["network"]`） |
| 动作 `id` 包内唯一、`hotkey` 格式（`is_valid_hotkey`） | 形如 `Ctrl+Alt+K` 的要求 |
| `entry` 指向的文件真实存在 | 显式指出 manifest 里写了什么 |
| 打包内容排除 | `__pycache__` / `*.pyc` / `*.log` / 隐藏文件 / 已有包 |
| **打完自校验** | 重开 zip 确认 manifest 可解析 + entry 在包内；不过则删包并报错 |

包结构固定为套一层 `<插件id>/` 前缀（与内置包一致），输出到 `plugin_store/`
后启动程序即可在「🏪 插件商店」看到。退出码：`0` 成功 / `1` 失败（可进 CI）。
> **不会删除**插件的私有数据目录 `float_data/plugins/<id>/`——
> 那是你的数据，重装插件后还能继续用。确认框里明确写了这一点。
> 卸载前若插件实现了 `on_uninstall(ctx)` 钩子，宿主会先调它。
>
> 手动删文件夹仍然可行（效果等价，只是不触发钩子，且需要重启程序）。

> 总开关关闭时：插件动作不挂右键菜单、不绑热键；**重新打开即时恢复**，
> 不会重新导入模块。单个插件的停用状态存在配置 `plugins_disabled` 里，
> 设置页「恢复默认设置」会把它清空（= 全部插件恢复启用）。

### 6.1 生命周期钩子（2026-09-27 起）

`BallPlugin` 除必须实现的 `create_actions` 外，还有三个**可选**钩子方法——
不实现也能正常工作，老插件零影响：

| 钩子 | 调用时机 | 典型用途 |
|---|---|---|
| `on_enable(ctx)` | 登记成功后（首次加载 **与** 从停用恢复都调） | 初始化缓存、预热数据、打开句柄 |
| `on_disable(ctx)` | 被停用 / 总闸关闭前（`unregister` 之前） | flush 未保存配置、关句柄、停定时器 |
| `on_uninstall(ctx)` | 卸载前（`rmtree` 之前，此时目录还在） | 导出数据、清理外部痕迹 |

```python
class MyPlugin(BallPlugin):
    def create_actions(self, ctx):
        return [MyAction()]

    def on_enable(self, ctx):
        ctx.logger.info("插件启用，开始预热")

    def on_disable(self, ctx):
        self._flush_cache()          # 停用前把缓存落盘

    def on_uninstall(self, ctx):
        self._cleanup()              # 卸载前收尾；此后目录会被删
```

**容错承诺**：钩子抛异常只记一条 warning 并**继续流程**——
登记照样成功、停用照样摘掉动作、卸载照样删目录。
异常会作为插件告警显示在插件中心卡片上，不会被静默吞掉。

> 钩子是可选的，不要为了「看起来完整」而空实现——`on_enable` 会在每次
> 「重新扫描」时随装配重跑，写重活会让扫描变慢。

## 7. 入口分配与冲突规则

- **热键**：核心功能优先级最高。插件声明的热键若与**快速捕捉**
  (`Ctrl+Alt+K`) 或**截图钉屏** (`Ctrl+Alt+S`) 相同（比大小写、忽略空格），
  该动作被跳过并记 warning。
- **插件之间**：同一热键被两个插件声明 → **先加载者赢，后者让位**并记 warning。
  加载顺序 = `plugins/` 下目录名的字典序。
- **动作 id**：全局唯一，重复 → 后者被拒绝登记并记 warning。
- **右键菜单顺序**：`打开主窗口 | [插件动作…] | 退出程序 | [运行时追加项…]`。
  插件动作按加载顺序排列，**不加子菜单层级**（层级会毁掉「快」）。

## 8. 容错承诺

以下情况**只跳过单个插件/单个动作，记 `logger.warning`，绝不影响其他插件和主程序**：

- `plugins/` 不存在（自动创建）/ 不可写
- `manifest.json` 缺失、JSON 损坏、缺必需字段、`id` 非法、`entry` 越界
- `api_version` / `min_app_version` 高于宿主（失败阶段 `version_mismatch`，
  与「manifest 写错」区分展示）
- `requires` 命中黑名单
- 入口模块不存在 / 导入抛异常
- 模块里没有 `BallPlugin` 子类 / 实例化失败 / `create_actions` 抛异常或返回非列表
- `create_actions` 返回了非 `BallAction` 对象
- 动作未在 `manifest.actions` 中声明
- 动作 `run()` 内部抛异常（由 `ActionRegistry.trigger` 兜住）
- 生命周期钩子 `on_enable` / `on_disable` / `on_uninstall` 抛异常
- 插件调用未授权的 `ctx.write.add_*`（返回 0，不写数据）/ 网络桥被拒
- 插件调用未授权的 `ctx.manage.*` 改删方法（返回 `False` / `0`，不动数据）
- 改删操作参数非法（id 不是正整数 / 文本参数不是字符串）→ 拒执行并记 warning
- 撤销令牌无效、已用过或超出保留窗口（最近 50 次）→ `undo_delete` 返回 `False`
- `.fpplug` 不是合法 zip / 内含路径穿越成员（zip-slip 防护，逐条剔除）
- 插件目录删除失败（文件被占用）→ 返回原因并展示，不崩

## 11. 读宿主数据：`ctx.data`

早期的插件只能弹窗，拿不到任何业务数据，能做的事很有限。现在 `ctx.data` 提供
五类只读访问器：

```python
tasks      = ctx.data.tasks()       # list[dict]
fragments  = ctx.data.fragments()   # list[dict]
notes      = ctx.data.notes()       # list[dict]
pomodoro   = ctx.data.pomodoro()    # dict（番茄钟当前状态）
knowledge  = ctx.data.knowledge()   # list[dict]（知识库段落：num / text / preview / hash）
```

**关键性质：返回的都是 `deepcopy` 出来的纯 dict / list。**

- 插件随便改、随便删字段，**动不了宿主数据**——不会出现「插件把任务列表清空了」这种事；
- 纯 dict 而非 ORM 对象，所以**不存在属性访问的版本耦合**，宿主内部类改了也不会牵连插件。

拿到的字段名与数据结构见对应 `*_manager.py` 的 `to_dict()`；`pomodoro()` 返回
的是状态快照字典。如果某个访问器在你的运行环境里取不到数据（例如数据层尚未
初始化），它会返回空列表 / 空 dict 而**不抛异常**——插件里请按「可能为空」来写。

> ⚠️ **`fetch()` 与访问器的空值语义不一致**：`ctx.data.fetch("tasks")` 在通道
> 缺失时返回 `None`，而 `ctx.data.tasks()` 统一兜底成 `[]`。自己用 `fetch()`
> 遍历数据源时记得判空。

#### `ctx.data.knowledge()`：位置型数据源（2026-09-28 起）

知识库是**唯一用「位置」而不是自增 id 寻址**的数据源，因此它不走
`to_dict()`（那段没有文本），而是宿主显式构造：

```python
[
  {"num": 1, "text": "完整段落文本", "preview": "首行摘要…", "hash": "a1b2c3d4..."},
  {"num": 2, "text": "...", "preview": "...", "hash": "..."},
]
```

| 字段 | 说明 |
|---|---|
| `num` | **编号，从 1 起**，对应知识库页面上显示的段号；等价于过滤后下标 + 1 |
| `text` | 段落完整文本（已 `strip`），**不含**编号前缀 |
| `preview` | 首行摘要，面板/卡片展示用；长段落已截断 |
| `hash` | 内容指纹（短哈希，忽略首尾空白）。改删操作的**唯一凭据**，见 4.5 节 |

**为什么一定要带 `hash`**：`num` 是位置，不是身份。删掉第 3 段，原第 5 段就
变成了第 4 段；而且 `.docx` 允许用户**随时用 Word / WPS 打开编辑**，插件拿到
的快照可能马上就过期了。所以任何针对既有段落的改 / 删都必须回传当初读到的
`hash`，宿主比对不上就**拒绝执行**——宁可失败，也不能改错段落。

过滤规则也要知道：知识库的**空行与少于 4 个字符的段落**在加载时被跳过，
所以 `num` 是**过滤后**的位置（面板编号与它一致）。这是 2026-09-28 统一的口径
（此前 `load()` 存的是原始 docx 下标，文档里一旦有空行就会与面板编号错位）。

> 只读是刻意的：写操作要经过宿主的校验、落盘、联动刷新（比如转任务要发信号刷
> 新页面）。给插件开写入口等于把这些约束全部绕过，所以当前不提供。插件要持久
> 化自己的状态，用下面的 `ctx.data_dir`。

### 私有数据目录：`ctx.data_dir`

```python
import json
import os

state_path = os.path.join(ctx.data_dir, "state.json")
with open(state_path, "w", encoding="utf-8") as f:
    json.dump({"last_run": "..."}, f, ensure_ascii=False)
```

- 实际路径是 `float_data/plugins/<plugin_id>/`，**首次访问时自动 `makedirs`**，
  不用自己建目录；
- 与宿主数据完全隔离，插件自己的文件不会污染 `float_data/` 根目录下的业务数据；
- 路径取的是宿主的 `get_data_dir()`，所以**打包前后位置都正确**，不要在插件里
  硬编码相对路径或用 `__file__` 往上找。

### 关于 `ctx.parent_window()`

返回主窗口对象（可能为 `None`，插件在无主窗口场景下被触发时）。用途是给
`QDialog` 之类挂个父窗口，让它居中于主窗口、跟随主窗口置顶：

```python
dlg = MyDialog(ctx.parent_window())
```

**注意这是宿主对象的裸引用，属于「逃生舱」**：只建议用来传 `parent`。不要从它
往上摸宿主的内部控件或直接调宿主方法——那些接口没有兼容承诺，宿主改版就可能
失效。业务能力请走 `ctx` 上正式暴露的方法。

## 12. 完整示例：周报草稿插件

`plugins/weekly-report/` 是本仓库内置的参考实现，也是插件能力的「活文档」。
读它比读本文档更快，建议直接打开源码对照。

它做的事：唤起后先选范围（今日 / 本周 / 自定义天数），然后汇总该区间内的

- **已完成任务**：按 `completed_at` 归入区间，按完成时间排序；
- **碎片**：按内容类别（链接 / 代码 / 路径 / 命令行 / 文本）分组；
- **番茄专注**：统计专注次数与累计时长；

拼成一份 Markdown 草稿，在预览窗里提供三个出口：**复制到剪贴板** /
**另存为 `.md`** / **写入 Obsidian vault**（未配置 vault 时该按钮置灰）。

它演示了本节全部关键点：

| 用到的能力 | 在插件里怎么用 |
|---|---|
| `ctx.data.tasks()` 等 | 拿数据做汇总，绝不写回 |
| `ctx.data.sources()` | 自省当前可用数据源，缺数据时给出降级文案 |
| `ctx.data_dir` | 记住上次选择的范围，下次默认沿用 |
| `ctx.parent_window()` | 预览窗挂父窗口，居中显示 |
| manifest `hotkey` | 声明 `Ctrl+Alt+W`，与核心热键冲突时自动让位 |
| 热键路径的模态风险 | 见下方「热键路径要延后开窗」 |
| `PluginDialog` 基类 | 窗口样式与主窗口一致，见第 13 节 |

`ctx.data` 除了四个命名访问器，还有两个自省方法，用来判断数据源是否真的可用：

```python
ctx.data.sources()      # ('fragments', 'notes', 'pomodoro', 'tasks') 之类的元组
ctx.data.has("tasks")   # bool
ctx.data.fetch("tasks") # 按名取；数据源缺失/读取失败 -> None（不抛）
```

注意 `tasks()` / `fragments()` / `notes()` 在数据源不可用时返回的是**空列表**
（内部做了 `or []` 兜底），而 `fetch()` 返回 `None`。所以插件里判「有没有数据」
优先看长度，而不是判 `None`。

### 热键路径要延后开窗

`run()` 在**热键触发**时是在原生事件过滤器里被调用的，此时直接 `exec()` 一个
模态对话框有事件循环重入风险；走**右键菜单**触发时则是在正常的 Qt 事件流里。
`weekly-report` 的统一处理是：把开窗动作延后一个事件循环回合再执行，
两条路径共用同一份逻辑，菜单路径只多付一个回合的代价。

```python
def run(self, ctx):
    holder = {}

    def _open():
        parent = ctx.parent_window()
        dlg = DraftDialog(parent)
        dlg.exec()

    QTimer.singleShot(0, _open)     # 两条路径都延后，行为一致
```

如果你在调试时遇到「插件弹窗后主界面卡住」或偶发崩溃，先检查是不是没有延后。

### `ctx.logger` 判空

`ctx.logger` 在极早期加载阶段可能为 `None`（加载器自身的日志调用也一律先判空）。
插件里若有日志语句，**建议同样判空**，否则异常堆栈会被 `run()` 外层的隔离机制
吞掉，你只能看到「动作执行异常，已隔离」而看不到真正原因：

```python
logger = getattr(ctx, "logger", None)
if logger is not None:
    logger.info("...")
```

验证脚本：

```bash
cd v4
python tools/run_gui_check.py tools/verify_weekly_report.py    # 65 项检查
```

## 13. 插件弹窗的 UI 规范

### 不要用裸 `QDialog`

裸 `QDialog` 会得到**系统原生外观**：方角、系统标题栏、灰底按钮，跟主窗口的
玻璃拟态风格完全割裂。宿主已经把这个问题的解决方案标准化了——用
`src.plugin_ui.PluginDialog`：

```python
from src.plugin_ui import PluginDialog, flash_button, make_section_label

class MyDialog(PluginDialog):
    def __init__(self, ctx, parent=None):
        super().__init__(ctx, title="我的面板", subtitle="副标题说明",
                         parent=parent, size=(860, 620))
        self.body_layout.addWidget(make_section_label("分组标题"))
        self.body_layout.addWidget(...)
        btns = self.add_footer([
            ("关闭", "secondaryBtn", self.accept),
            ("确定", "primaryBtn", self._do_ok),
        ])
```

`PluginDialog` 是 `src.glass_dialog.GlassDialog` 的插件友好封装，
自动带来这些与主窗口一致的要素：

| 要素 | 效果 |
|---|---|
| 无边框 + 半透明底 + 圆角 | 圆角真正生效，无系统标题栏 |
| `GlassPanel` 玻璃壳 | 半透明填充 / 顶部高光 / 双色描边 / 噪点 |
| `paintEvent` 手绘外圈阴影 | 与主窗口同款柔和投影 |
| 自绘标题栏 | 图标 + 标题 + 副标题 + 关闭按钮，可拖动移动窗口 |
| 复用主窗口 QSS | **跟随 light/dark 主题自动换肤** |

### 可用的 objectName

因为直接复用主窗口 QSS，这些名字拿来即用：

| objectName | 用途 |
|---|---|
| `primaryBtn` | 主操作按钮（主色渐变底 + 深墨字） |
| `secondaryBtn` | 次操作按钮（主色淡底 + 主色描边） |
| `dangerBtn` | 危险操作（红） |
| `iconBtn` | 图标按钮（配 `property("danger","true")` 变红） |
| `glassCard` | 内嵌卡片（第二层玻璃底 + 圆角） |
| `sectionLabel` | 小标题（13px / 600 字重） |
| `hintLabel` | 灰色提示（11px / placeholder 色） |
| `settingsSeparator` | 1px 分隔线（用 `make_separator()` 建） |

`QPlainTextEdit` / `QLineEdit` / `QDateEdit` 等输入控件在 QSS 里**已有通用规则**，
不用设 objectName 就自带圆角、焦点态、禁用态。**反之不要臆造 objectName**
（比如 `panelInput` 并不存在），写了不生效还容易误以为样式没加载。

### 布局约定

- 所有内容必须加到 **`self.body_layout`**，不要直接挂到对话框上——
  `GlassDialog` 的布局里标题栏占顶部，直接挂会压到标题栏下面；
- 底部按钮用 **`self.add_footer([...])`**，它已自动右对齐并接好 `clicked`；
  **不要再手动 `clicked.connect` 一次**，否则每次点击触发两次（落盘/弹窗翻倍，
  这个坑真的踩过）；
- 需要临时反馈时用 `flash_button(btn, "✅ 已复制")`，它会短暂改文案并禁用按钮，
  比弹 MessageBox 打断操作更轻。

## 14. 让 AI 按用户指令改数据（动作协议模式，2026-09-28 起）

这一节不是 API，而是一套**已被验证的交互模式**——AI 助手插件用它把
「自然语言 → 改应用数据」做成了安全可用的功能。如果你的插件也要接大模型，
建议直接照搬，别自己发明。

### 14.1 为什么不用原生 function calling

本地跑的是 Qwen3-4B 量化版，对 JSON schema 的遵循度**不稳**（云端
DeepSeek 支持很好）——同一个接口要同时喂两种后端，就得选两端都能执行的
约定。方案是**提示词约定 + 应用侧解析**：模型在回复**最后**输出一个
```` ```actions ```` 块，插件解析后按白名单执行。

代价是小模型偶尔输出格式错误。应对原则只有一条：**宁可整块不执行并如实
提示，也绝不去猜意图**——猜错就是改了用户的数据。

### 14.2 三件事必须分开做

| 层 | 职责 | 别做的事 |
|---|---|---|
| 提示词 | 告诉模型有哪些 op、id 只能取自数据里的真实编号 | 别在提示词里承诺做不到的操作（未授权就别下发协议） |
| 解析器（纯函数） | 校验结构 / op 白名单 / **id 必须真实存在于快照** / 参数类型 / 条数上限 | 别在这里碰 UI，也别执行任何写操作 |
| 执行器 | 分级：新增直接做，改删先弹确认卡 | 别让模型直接决定「要不要确认」 |

### 14.3 解析器的容错契约

```python
clean, actions, errors = parse_actions(reply_text, snapshot)
```

- **没找到动作块** → 正文原样返回、零动作零错误；
- **找到动作块** → 正文返回**剥掉动作块后的内容，可能是空串**。
  空串表示「这条回复除了动作什么都没有」，调用方据此**不渲染文字气泡**
  （否则用户会看到一坨 JSON）。
- 坏 JSON / 结构不对 → **整块**不产出动作 + 给出原因；
- 单条不合格（未知 op、id 编造、参数类型错）→ **只丢那一条**，其余照常；
- 条数超上限 → 截断并提示（防模型刷屏式输出）。

> 一个容易忽略的坑：只认 ```` ```actions ```` 围栏还不够——普通问答里也
> 可能出现 JSON（用户贴配置问「这是什么」）。兜底识别路径（`json` 围栏 /
> 裸 JSON）必须先判断「这段 JSON 是否含 `actions` 数组」再决定要不要从
> 正文里剥离，否则会把用户的问题从回复里删掉。

### 14.4 分级确认与撤销

- `write` 级（新增）→ 直接执行，结果汇总成一张结果卡；
- `manage` 级（改删）→ 渲染确认卡列出**将执行的操作（含目标记录标题）**，
  用户点「执行」才落库，点「取消」则零改动；
- 删除成功后结果卡带「↩ 撤销删除」按钮 → 逐令牌调 `ctx.manage.undo_delete()`，
  并在按钮上回写恢复结果。

授权前置守卫：协议只在授权时才下发，但模型仍可能硬输出动作块。此时
**不要**把注定被宿主拒绝的动作渲染成确认卡（用户点了只会看到一排失败），
应直接如实说明「未执行 + 原因」。

### 14.5 位置型数据的两个额外约定（2026-09-28 起）

AI 助手现在也能改**知识库**（`add_knowledge` / `update_knowledge` /
`delete_knowledge`）。知识库用编号寻址，比自增 id 的数据源多两条硬约定：

1. **改删必须绑定快照里的 `hash`**。`parse_actions` 在解析时就把该编号当前
   的 `hash` 抄进 `args["expect_hash"]`——模型**不需要（也没法）自己编**
   指纹；快照里那段没有 `hash` 就整条丢弃。用户看到确认卡→点执行的这段时间
   里如果段落变了，宿主比对不上就拒绝，**不猜、不改错段**。
2. **同批多个删除要按编号降序执行**。这是位置型数据独有的坑：先删 4 号再删
   6 号，删完 4 号后原 6 号已经变成 5 号，第二条就错位了。纯函数
   `_order_actions()` 负责这个排序——它只重排**同批动作的执行顺序**，不改
   动作内容，新增/修改类的相对顺序保持不变。

失败时的提示也要区分：知识库改删失败很可能是「内容已变」或「被 Word 外部
改动过」，所以要明确引导用户去知识库页点「🔄 重新加载」再试，而不是笼统说
「操作失败」。
