## 4. P0：成熟框架的最低门槛

### P0-1　manifest 版本契约（`api_version` / `min_app_version`）

**问题**：`REQUIRED_FIELDS = ("id","name","version","entry")`，宿主与插件之间没有版本握手。
API 一旦演进（例如 PluginContext 改签名），老插件会以「动作创建失败」这类表层错误暴露，排查成本高。

**方案**

1. 新增宿主版本常量（项目当前无版本常量，先建）：

   ```python
   # v4/src/app_version.py
   APP_VERSION = "4.6.0"          # 三段式，与 CHANGELOG / Release tag 对齐
   PLUGIN_API_VERSION = 1         # 契约版本，破坏性变更才 +1
   ```

2. `validate_manifest()` 增加可选字段校验（`plugin_loader.py:128`）：

   | 字段 | 类型 | 缺省 | 规则 |
   |---|---|---|---|
   | `api_version` | int | 1 | 非 int / ≤0 → 拒载；`> PLUGIN_API_VERSION` → 拒载（插件要求更新的宿主） |
   | `min_app_version` | str | "" | 三段式点分数字；宿主版本低于它 → 拒载 |

3. 新增失败阶段：

   ```python
   STAGE_VERSION_MISMATCH = "version_mismatch"
   # FAIL_HINTS 补：「插件要求的宿主 / API 版本高于当前程序，请升级 FloatPulse 或联系插件作者」
   # stage_label：「版本不匹配」
   ```

4. 归一化结果里带上 `api_version` / `min_app_version`，供面板卡片展示（可选）。

**验收**

- 新增 `tests/test_plugin_version.py`：缺字段按 1 处理 / 非 int 拒载 / api_version 高于宿主拒载 / min_app_version 高于宿主拒载 / 相等放行 / 旧插件（无此字段）零影响。
- 老插件 weekly-report / ai-assistant 仍能加载（回归）。
- `git grep REQUIRED_FIELDS` 确认没有第二处 manifest 校验。

**风险**：低。纯加载期校验，不影响运行期。

### P0-2　启停状态持久化

**问题**：`PluginsPanel._toggle_plugin()`（`plugins_panel.py:577`）只改内存中的 `BallAction._enabled`，
配置不落盘 → 重启后所有插件恢复启用，用户对「停用」的预期落空。

**方案**

1. 配置三件套同步（`src/config.py`，铁律：三处都要加，`list` 类型**不进** `_CONFIG_RANGES`）：

   ```python
   DEFAULT_CONFIG = {..., "plugins_disabled": []}     # 被停用的插件 id 列表
   _CONFIG_TYPES  = {..., "plugins_disabled": list}
   ```

2. 宿主侧：在 `_apply_plugins()`（`knowledge_ball.py:2672`）里，`plugin_loader.load_all()` 之后按配置回置状态：

   ```python
   for pid in config_manager.get("plugins_disabled", []) or []:
       plugin_loader.set_plugin_enabled(pid, False)
   ```

3. `PluginLoader` 新增 `set_plugin_enabled(plugin_id, on) -> int`（遍历 `LoadedPlugin.actions_raw` 调 `registry.set_enabled`）。

4. 面板 toggle 时写配置：新增 `_host` 侧写入路径（复用设置页既有的 `config_manager.set(...)` + 持久化调用，
   不新增跨层 API），成功后 `refresh()`。

5. 恢复默认设置必须回写该键（`settings_panel` 恢复默认逻辑里补 `plugins_disabled` → `[]`）。

**验收**

- 停用一个插件 → 重启程序 → 仍为停用态，菜单/热键都不出现。
- 恢复默认设置 → 全部插件回到启用。
- 新增测试：配置往返、未知 id 不报错、面板按钮文案与实际状态一致。

**风险**：低。注意 `config_manager.set` 后要触发既有持久化（不要自己造写盘路径）。

### P0-3　卸载入口

**问题**：面板只有「打开目录」，删除插件靠用户手动删文件夹，且 `float_data/plugins/<id>/` 的私有数据不会被清理。

**方案**

1. `PluginLoader.uninstall(plugin_id) -> tuple[bool, str]`：

   - 前置断言：`is_safe_plugin_id(plugin_id)` 为真，且目标目录满足 `_within(target, self.plugins_dir)`（`plugin_loader.py:740`），**越界一律拒绝**；
   - 顺序：`unregister` → `on_uninstall(ctx)`（若 P1-1 已做）→ `shutil.rmtree(target)` → 从 `_loaded` 移除 → `rescan()`；
   - **不删** `float_data/plugins/<id>/`（插件私有数据保留，卸载确认框里明说）。

2. 面板卡片加「🗑 卸载」按钮 → 二次确认（`QMessageBox` 或 `PluginDialog` 风格的自绘确认框），
   确认文案必须列出**将被删除的绝对路径**，并说明「插件私有数据保留在 data 目录」。
3. 卸载后自动 `_notify_menu_rebuild()` + `refresh()`。

**验收**

- 卸载 weekly-report → 目录消失、菜单项消失、热键解绑、重启不再加载。
- 边界测试：非法 id（含 `..`）、目标目录在 plugins_dir 之外 → 拒绝且不删任何文件。
- 卸载失败（文件被占用）→ 返回原因字符串并展示，不崩。

**风险**：中（涉及删除）。必须二次确认 + 路径白名单校验；不碰插件数据目录。

## 5. P1：解除能力天花板

### P1-1　生命周期钩子

**问题**：`BallPlugin` 只有 `create_actions()`。插件无法感知「被启用/被停用/被卸载」，
需要在停用前 flush 缓存、关闭句柄的插件无处下手（AI 助手的配置保存目前靠关窗兜底）。

**方案**：`BallPlugin` 增加**三个可选方法**（不进 `@abstractmethod`，老插件零影响）：

```python
class BallPlugin(ABC):
    def on_enable(self, ctx):   """登记完成后调用（首次加载 与 从停用恢复 都会调）"""
    def on_disable(self, ctx):  """被停用 / 总闸关闭前调用"""
    def on_uninstall(self, ctx):"""卸载前调用（此后 data_dir 不会被删）"""
```

调用点：

| 钩子 | 调用位置 |
|---|---|
| `on_enable` | `PluginLoader._register_plugin()` 登记成功后（`plugin_loader.py:625`） |
| `on_disable` | `PluginLoader.deactivate()` 内，`unregister` 之后 |
| `on_uninstall` | `PluginLoader.uninstall()` 内，`rmtree` 之前 |

统一走一个 `_safe_hook(lp, name, ctx)`：无该方法则跳过；抛异常 → 记 `warning` **继续流程**，绝不反噬宿主。

**验收**：新增测试——无钩子插件不受影响 / 钩子抛异常不影响登记与卸载 / 三个调用点各触发一次（用探针插件计数）。

### P1-2　受限写能力 `capabilities: ["write"]`

**问题**：`ctx.data` 是**只读**快照。插件能读任务/碎片/笔记，却写不回去 ——
AI 助手「把整理结果存成笔记」这类需求只能靠用户自己复制粘贴，插件价值被打折。

**方案**：沿用已验证的权限模型（声明 + 宿主桥），**不放开对象访问**：

1. `KNOWN_CAPABILITIES` 增加 `"write"`；`FAIL_HINTS` 与面板 `cap_labels` 同步（`{"write": "✍ 写入数据"}`）。
2. `PluginContext` 新增 `write` 门面（与 `http_post_json_async` 同构：未声明能力 → 记 warning 返回失败值，不抛异常）：

   ```python
   ctx.write.add_fragment(content, source="")  -> int   # 返回 fragment_id，0 = 未写入
   ctx.write.add_task(title, note="", deadline="") -> int
   ctx.write.add_note(title, content="") -> int
   ```

3. 宿主注入 provider（装配点：`knowledge_ball.py` 构建 `plugin_ctx` 处，与 `http_post_async` 并列）：

   ```python
   write_providers = {
       "fragment": lambda content, source: fragment_manager.add_fragment(
           TYPE_PLUGIN, content, source or f"插件:{plugin_id}"),
       "task":  lambda title, note, deadline: task_manager.add_task(title, note, deadline),
       "note":  lambda title, content: note_manager.add_note(content, title),
   }
   ```

   - `source` 缺省自动带 `插件:<id>`，落库后可追溯来源；
   - 写入成功 → 触发既有刷新链路（`main_window.refresh_*` / `ball.refresh_badge`），与卡片数据变更保持一致；
   - **不做**更新与删除（改/删的破坏性远大于新增，起步阶段不开口子）。

4. 内容护栏：空内容 / 非字符串 → 拒绝并返回 0；长度上限（建议 8000 字符）截断并记 warning。

**验收**

- 未声明 `write` 的插件调 `ctx.write.add_*` → 返回 0 + warning，**不抛异常、不写数据**（安全测试必过）。
- 声明后写入 → 数据落盘、UI 刷新、来源字段正确。
- 新增 `tests/test_plugin_write.py`（纯逻辑：鸭子类型 provider，无 GUI）。

**风险**：中。首次开放写路径，必须走「能力声明 + 宿主桥 + 只增不改删」三重约束。
